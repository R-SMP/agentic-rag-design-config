Database: parameter schema

Every saved session records which parameter set its values belong to. The database keeps each set as a numbered version, and a session can be saved only when one version matches this setup's parameters exactly. Uploading adds this setup as the next version, or does nothing when the latest version already matches. Every version is listed under Database schema in the side menu.

Which agent holds each role of the 7-agent system in the reduced topologies. Sessions saved under any topology stay retrievable under the others through this table.

  • Retrieval works both ways. An agent can read every past answer addressed to a role it holds here: a 3-agent Design Engineer reads answers addressed to the DCIC, DCII and Tool Caller, and a 7-agent DCIC reads answers addressed to a Design Engineer. When a search result names an agent this system does not have, the response opens with one line telling the agent which agent here holds that role.
  • Questions for Saved Sessions map downward only. Write the tables in 7-agent names.   • Changes take effect for the next session. Customizing this table is planned (TODO F102).

Model context windows

How large a context window each model has, in input tokens. The Context Pruner uses this to decide when an agent's history has grown too long: it prunes at max(min-threshold, min(fraction × window, max-threshold)), counting the system prompt as well as the history. Rows are matched as name prefixes, longest first, so claude-opus-4-5 (200k) wins over claude-opus for that model — which matters, because the window varies by version within a family. Keep the short family rows conservative. Anthropic models are refreshed live from the provider API at session start and override this table; OpenAI exposes no window, so those rows are maintained here. Changes take effect for the next session.

Database — developer console

This view exposes destructive database operations. Enter the password configured on the server (PASSWORD_DATABASE_WEB_UI) to unlock it. The password is held in browser memory only — refresh the page and you'll need to re-enter it.

Reset the database to a clean state

Type the phrase reset_database in the box below and press Enter or click Send to permanently delete:

  • All rows in sessions (cascades to chunks, dc_attempts, dc_attempt_parameters)
  • All rows in rag_queries

Preserved:

  • dc_parameter_schemas (the 17-parameter schema seed)
  • The session_counter SEQUENCE — the next session ID continues from the current count, not reset to 1. Manually reset via psql (ALTER SEQUENCE session_counter RESTART WITH 1;) if you want IDNNN to restart.

This action is irreversible. Make sure you are pointed at the right database.

Clear previous-sessions folder

Type the phrase clear_previous_sessions in the box below and press Enter or click Send to permanently delete every subdirectory inside the Railway volume's previous_sessions/ folder. This removes the on-disk cache of past-session artefacts that retrieve_attempt / retrieve_user_inputs fall back to when the canonical store is unreachable.

What gets wiped:

  • Every ID<NNN>_YYYYMMDD_HHMMSS/ directory directly inside previous_sessions/ on the currently- running container's volume
  • All per-attempt artefacts inside those directories (renders, meshes, description.txt, per-agent histories)

What is preserved:

  • The Postgres database (sessions, chunks, dc_attempts, …) — use the red Reset the database box for that
  • The R2 bucket — past-session artefacts archived to R2 are untouched
  • The previous_sessions/ folder itself (only its children are removed)
  • The current in-flight session (if any) — only sessions already archived to previous_sessions/ are affected

This action is irreversible on the container's local volume. If you need any of these files, re-download them from R2 first (canonical archive) before running this. Scope is the current Railway container only — other deploys / local checkouts are untouched.

Session ignore list

Session IDs listed here are EXCLUDED from database_search results and skipped (with a status="ignored" marker) by retrieve_user_inputs and retrieve_attempt. Useful when you want the next sessions to neglect content from specific previous sessions during retrieval. Effect is immediate: the list is read fresh on every retrieval call.
