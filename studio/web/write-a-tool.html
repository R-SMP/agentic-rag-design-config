Write a tool

How the agents build and look at a design: a tool is a folder of the setup with a manifest, its code (or a model file) and the texts it owns.

What a tool is

A tool lives in setups/<setup>/tools/<name>/: its manifest tool.yaml, its Python code (or, for a generator or a geometry tool, an OpenSCAD model the engine runs), and in prompts/ the texts the agents read about it. The engine reads the manifest, builds the agents' tool from it and gives it to the agents that hold its roles; the code does only the configurator's own work. There are three kinds:

  • Helper: one plain Python function the agents call, for example to draw a diagram of an attempt. It returns the text the agent reads.
  • Generator (the Studio's model builder): builds the design from an attempt's parameters.json (its model file), then makes its pictures. The agents' main tool; a setup has one.
  • Geometry tool (the Studio's download builder): builds the model from the parameters for a generator (its geometry tool setting) and for the web app's Download buttons. The engine calls it; an agent never does.

Start one

In the Studio, Tools › Add a tool starts a tool from a template of its kind (each a small working starter), as a copy of a tool, from your Python script, or from a CAD file (see OpenSCAD models). A script's function is chosen in the wizard; a helper's function names the tool (the engine calls the helper by its function's name). Then change its code in its Files tab (Advanced), its manifest and its texts in Tool details (a form) or tool.yaml (Advanced). Every change to a manifest is checked by the engine before it is saved.

The code

A helper is one function with type hints, named by the manifest's entrypoint (file.py:function). The engine builds the agents' tool from its signature and the manifest's description. The first argument is usually the path of an attempt's parameters.json:

def my_tool(parameters_path: str) -> str:
    values = json.loads(Path(parameters_path).read_text(encoding="utf-8"))
    ...
    return "the text the agent reads"

A generator provides two functions, named by build and render:

  • build(inp) -> BuildResult writes the model file at inp.model_path and returns a summary for the agent;
  • render(inp) -> RenderResult writes the pictures into inp.attempt_dir and returns a report.

inp holds params (the attempt's values, already checked against parameters.json), attempt_dir, model_path and settings (the tool's own settings). The engine does the rest: it checks that the path the agent passed is an attempt's, reuses a model that is already there (an attempt is never overwritten), turns an error into the text the agent reads, and joins the summary and the report into the tool's answer.

A geometry tool is one function, make_model(params) -> GeometryResult: it returns the model's content (GeometryResult(model=..., vertex_count=...)) and writes nothing.

All of these come from engine.tooling. For a failure the agent should read, raise ToolError("what went wrong") (or, in a helper, return a text starting with Error:).

The manifest: tool.yaml

  • name (the folder's name: lower case, digits, _), display_name, kind (helper, generator or geometry).
  • roles (a helper or a generator): which agents get it, by what they do — tool_runner, parameter_author, parameter_checker, output_inspector, input_extractor, planner, hub, receptionist. The engine gives it to whichever agent holds the role in the running team.
  • description: what the agents read about the tool — what it does, what to pass, what it returns. args (a generator: exactly parameters_path) describes its argument.
  • entrypoint (a helper, a geometry tool) or build / render (a generator): file.py:function.
  • outputs: a generator's model_file (e.g. my_model.obj), model_format (obj), up_axis (y or z) and images; a geometry tool's model_format only.
  • list_order: a tool-runner tool's place in the tool runner's numbered tool list.
  • settings (optional): values the user changes in Workflow Settings — bool, enum (with values) or tool (a geometry tool to use) — each with a default; a generator reads them in inp.settings. switch (optional) turns the whole tool on or off.
  • secrets (optional): the environment variables it needs, by name only ({env: MY_KEY, required: true, description: ...}). Their values go in .env or the deployment's variables, never in the setup.
  • prompt_slots (optional): the texts it owns (they live in its prompts/ folder and leave with it).
  • backend, model, parts, fixed, detail, timeout: a model the engine runs instead of code (OpenSCAD models).

Pictures

A picture of view V is the PNG render_V.png, written into the attempt folder the tool is given. Each view is listed under outputs.images with its view, file, order, default_enabled (its switch in Workflow Settings) and compression (3d_render or cross_sections: how much it is shrunk before a model sees it). A tool that makes pictures also says fill_on_save: whether the save step may ask it for a picture an attempt is missing.

The texts it owns

A tool-runner tool has an entry in the tool runner's numbered list, prompts/tool_list_entry.md: one paragraph saying what it does and when to call it. The other texts it owns (prompt_slots) are edited in its Tool details, like every text field. Elsewhere, a part of a text can be kept only while a tool is in the setup (<<IF:tool:name>>…<</IF:tool:name>>).

Test it

  • Test (on a tool's card, or its page's Test tab) runs it the way the agents call it — on the parameters' defaults, a picture sample or values you type — in a throw-away attempt folder, and shows what it answers, how long it took, its pictures, its model, any error with its traceback, and every mismatch with its details (a short verdict first). Nothing in the setup changes.
  • Validate runs every tool once on the parameters' defaults, and says when this computer lacks a package or a program a tool needs (a warning: the deployment may have it).
